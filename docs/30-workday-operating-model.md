# 30. 勤務モデル(V8, 2026-07-27) — 「全員が働く会社」の運用設計

背景: 代表者指摘「AI社員が全然働いていない」。実測(DB)では実働6名・ゼロ稼働8名だった。
原因は2つ: (1) 楓・桔梗・美月・陽葵に業務が配線されていなかった (2) 凛・梓はエージェントとして働いてもDBタスクが作られず「常に待機」に見えた。
本書はその恒久対策(シフト制・全員配置・見える化)を定める。調査(凛)・実装は2026-07-27。

## 1. 正直な前提(嘘をつかないための明記)

- **AI社員は常駐しない。** 稼働するのは、代表者(または将来のcron)がセッション(/kickoff等)を実行している間だけ。「8時間働き続ける」は常駐ではなく、**1日3シフトの実行**で近似する
- 「働いているように見せる」ための空タスクは作らない。各シフトのタスクは実出力(note/調査/画像)を必ず残す
- トークン・APIコストはシフト数に比例する。生成上限(投稿3本/日等)は変えない

## 2. 1日の勤務時間割(3シフト)

| シフト | コマンド | 稼働する社員 | 業務 |
|---|---|---|---|
| 朝(9:00頃) | `/kickoff` | 葵・昊・琴葉・椿・紬・紫苑(+ニュース日は凛・梓) | 投稿の企画→コピー→レンダリング→QA→承認キュー |
| 昼(13:00頃) | `/noon-run` | 葵・桔梗・凛・椿 | 進行管理(停滞チェック)・翌日のネタ収集・ストーリー1本 |
| 夕(17:00頃) | `/evening-run` | 葵・湊・美月 | 実績値/計測期限の確認・代表者向けまとめ・日報/バックアップ/run終了 |
| 週1(金) | `/weekly-review` | 葵・湊・蓮・楓 | 週次分析・改善仮説・PMO監査・議事録 |

- 全員に配線済み: 葵(全)・昊/琴葉/紬/椿/紫苑(朝)・桔梗/凛(昼)・湊/美月(夕)・蓮/楓/湊(週次)・梓(ニュース検証時)
- 陽葵(DM支援・第2段階専用)は実働ゼロのため**2026-07-27に削除**(migration 17。タスク履歴ゼロを確認の上)

## 3. 自動実行(8h稼働に近づけるオプション・代表者の選択)

- **手動運用(現在)**: 代表者が朝・昼・夕に各コマンドを実行(所要: 見守りゼロでも各10〜30分でシフト完了)
- **自動実行(2026-07-27設定済み・launchd採用)**: macOSのLaunchAgents(`config/launchd/com.bloom-l.*.plist` → `~/Library/LaunchAgents/`)で平日3シフト+金曜週次を自動実行する。crontabはサンドボックス/TCCでハングしたため不採用(二重登録なしを確認済み)
  - スケジュール: 平日 9:00 kickoff / 13:00 noon-run / 17:30 evening-run、金 16:00 weekly-review。ログ: `logs/cron/*.log`
  - 停止: `launchctl bootout gui/$(id -u)/com.bloom-l.<name>` / 再開: `launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/com.bloom-l.<name>.plist` / 手動即時実行: `launchctl kickstart gui/$(id -u)/com.bloom-l.<name>`
  - **前提**: Macが起動しておりログインセッションがあること(スリープ中は次回起床時にまとめて実行されない場合がある。確実性を上げるなら「システム設定→エネルギー」でスリープ調整)
  - **認証(実測 2026-07-27)**: launchd起動の`claude`はKeychainへアクセスできず無反応で固まる(実測: CPU 0%でハング。最小環境では「Not logged in」)。対策として各シフトは `scripts/shift-runner.sh` 経由で起動し、**`~/.claude/bloom-cron-token.txt`**(代表者が `claude setup-token` で発行・chmod 600)から `CLAUDE_CODE_OAUTH_TOKEN` を読み込む。トークンはrepo・会話・plistに置かない
  - **制約(実測済みの事実)**: ヘッドレス実行ではclaude.aiコネクタ(Canva)が使えない可能性が高く、その場合は表紙もSatoriで生成(設計済みフォールバック)。公開(Instagram実投稿)は引き続き代表者のみ。`--dangerously-skip-permissions`で実行される(スキル側のallowed-toolsとCLIの構造ガードが安全境界)
- **クラウドCron(V6準備済み)**: PostgreSQL移行・本番認証・デプロイ完了までnot_ready(fail closed)。ローカルDBのままではクラウド定期実行は不可(docs/27)

## 4. Threads参入の判断材料(凛の調査 2026-07-27。出典はnote成果物参照)

- **事実**: Threads公式APIは2024-06提供開始。無料。テキスト(500字)・画像/動画・カルーセル(20点)投稿と閲覧/いいね等の分析取得が可能。24hあたり最大250投稿アクション。要Meta開発者アカウント+ビジネスアカウント連携
- **事実(留保付き)**: 日本のMAUはMeta非公開。推計は1,000万〜1,700万で資料によりばらつき
- **未確認**: HP制作会社/BtoBローカルでの成功事例は発見できず(農業・メディアの事例のみ)。効果は未知数
- **提案(推測・要CEO判断)**: Instagram投稿のテキスト再編集による**週2〜3本の試験運用を3ヶ月**行い、数値で本格参入を判断する。なお**自動投稿は現行ルール(外部への自動送信禁止)に抵触するため、導入するなら代表者の明示決定(DECISIONS追記)が必要**。現時点では未導入

## 5. 見える化のルール

- サブエージェントを起動する仕事は、原則**DBタスク(create-task→start→submit)を必ず作る**(オフィス画面の稼働表示・日報集計の根拠)
- 例外: 紫苑のQA(qaタスクで記録)・椿のレンダリング(render/hybrid-registerが自動記録)は既存の仕組みどおり
