# 15. KPIと分析

## 1. 原則【確定§16】

- 現状値(2026-07時点: 投稿約1本・フォロワー約17人)を基準に、**30日ごとに再設定**
- 目標値は根拠付きの**提案**であり、確定値として捏造しない。実績が乏しい初月は「計測基盤づくり」を最重要目標とする
- フォロワー数は参考指標。最終成果は 認知→DM相談→見積もり→受注

## 2. KPIツリー

```
受注 ← 見積もり ← DM相談 ← プロフィール閲覧/リンク遷移 ← 到達(リーチ・保存・シェア) ← 投稿の質×継続
                                                    ↑ 運用品質(承認率・失敗率・所要時間・代表者時間)
```

## 3. 指標定義と初期目標(30日)【推奨RC-7 — すべて提案値】

### 経営成果(月次)
| 指標 | データ源 | 初月目標(提案) | 根拠 |
|---|---|---|---|
| DM相談数 | 代表者入力(MVP)/ dm_items(第2段階でDM支援実装後) | 2件 | 週3投稿×4週で地域到達を作る初月の現実値。0でも失敗ではなく導線検証を優先 |
| 見積もり数 / 受注数 / 売上 | 代表者入力 | 計測開始(目標未設定) | 母数不足のため2か月目から設定 |
| 顧客獲得単価 | 費用(0円+代表者時間)÷受注 | 計測のみ | 時間コストを日報の代表者作業時間から算出 |

### SNSファネル(週次、post_metricsから)
| 指標 | 初月目標(提案) | 根拠 |
|---|---|---|
| 投稿あたりリーチ | 300 | 同規模地域アカウントの一般的初期値。実測1か月で再設定 |
| プロフィール閲覧(月) | 150 | リーチの5%想定 |
| 保存+シェア(投稿平均) | 5 | 保存型コンテンツ(柱⑥)の狙い |
| DM開始(月) | 2 | 上記経営成果と一致 |
| HP遷移 | HP完成後に追加 | — |

### 運用品質(週次、システム自動集計)
| 指標 | 目標(提案) | 集計方法 |
|---|---|---|
| 投稿継続率 | 計画比100%(週3) | posts.published / calendar計画 |
| 投稿案の承認率 | 70%以上 | approvals(approved/(approved+rejected+revision)) |
| 修正回数 | 平均1回以下/投稿 | artifacts.version |
| 事実確認エラー(公開後) | 0件 | 代表者記録 |
| 誤字・ブランド違反(QA検出) | QA通過後0件 | qa_reviews |
| 生成→承認の時間 | 24h以内 | イベントタイムスタンプ |
| 代表者の作業時間 | 30分/日以内 | UI操作ログからの推定+自己申告 |
| AI利用量 | limits内 | usage_records |
| タスク失敗率 | 10%未満 | tasks |

## 4. 計測フロー

1. 投稿3日後・7日後に「実績値入力」タスクが承認キュー横に出る(代表者がInstagramインサイトから転記、5分以内の項目数に絞る)
2. 湊(分析)が週次で集計 → 週報(何が保存されたか・どの柱が効いたか・改善仮説)
3. 30日ごと: 月報+**KPI再設定の提案**(根拠: 実測分布)→ 代表者が承認して次月目標に確定(audit_log記録)

## 5. 改善ループ

- 仮説は「柱×形式×CTA」の組み合わせ単位で記録し、次週の企画配分に反映(蓮→昊)
- 投稿数が10本未満の間は統計的断定をしない(湊の禁止事項)。「傾向の可能性」として報告

### V3追補(2026-07-13 実装反映)
- 日報基盤を実装(`buildDailyReport`)。**全項目を通常コードで集計**(AI不使用)。推定値は「推定」と明示し、売上・成果は捏造しない(未入力は未入力のまま)
- 集計項目: 作成投稿と現在状態 / 完了・失敗タスク / 権利ブロック / 承認待ち / 社員別稼働 / 推定利用量 / heavy昇格回数 / エージェント起動回数 / 停止理由 / 代表者への依頼 / 翌日の推奨作業
- CLI(`company daily-report`: 湊のreportタスク経由で冪等保存)とUI(`/reports`)の両方から確認可能
