# 01. 確定要件

確定仕様(`Bloom-L_AI_Company_ClaudeCode_Prompts.md` §1〜§22)から【確定】事項のみを整理する。
本書に含まれない事項は確定ではない。推奨・仮定は `02` および各設計書を参照。

## 1. 事業とゴール

- Bloom-Lは2026年4月ごろから活動するフリーランス事業。提供: HP制作 / LP制作 / 簡易DX・自動化スクリプト / SaaS / 業務システム
- Instagramは開設済み。投稿約1本、フォロワー約17人、プロフィール設定済み
- 最終目的: 泉州地域の見込み客の認知 → InstagramのDM相談 → 見積もり → 受注。フォロワー数は参考指標
- 仕組み全体の名称: Bloom-L AI Company。初期部門: Bloom-L AIマーケティング部

## 2. 対象顧客・地域・サービス優先順位

- 初期地域: 大阪府 泉州地域。拡大は運用モデル確立後に検討
- 最初の主要顧客: まだHPを持っていない会社・個人事業主
- 美容サロン支援は将来候補(初期3か月の主対象にしない)
- 重視する価値: 地域密着・相談しやすさ・迅速さ
- 受注優先順位: ①HP制作 ②LP制作 ③簡易DX・自動化 ④SaaS ⑤業務システム。SaaS・業務システムは信頼獲得後の上位提案

## 4. ブランド

- ブランド名: Bloom-L / 中核: 「コスパに優れたITサービスで、まず身近な人や地域の事業者を幸せにする」
- 格安ではなく「投資対効果が高い」会社として表現する。顔出しは行わない
- 既存ロゴ・ブランドカラーあり。素材は後から所定フォルダへ配置(UIはプレースホルダー+デザイントークンで先行)

- 専門用語は顧客の利益に翻訳して発信する(例: Next.js → 表示速度・使いやすさ・更新性・検索・信頼性)

## 5. SNS方針

- 主軸: Instagram。MVPは全SNS同時運用を目標にせず、Instagram向けコンテンツの質と継続性を検証
- 将来検討: Googleビジネスプロフィール(地域検索)/ Threads・Facebook(再利用)/ TikTok・YouTube Shorts(型確立後)。X・LinkedIn・長尺YouTubeは優先度低
- コンテンツの柱(6本): ①IT・AIニュース ②現代のHPの役割 ③HP導入で事業がどう変わるか ④見込み客が気になるWeb・ITトピック ⑤Bloom-Lの実績・技術紹介 ⑥泉州のHP未保有事業者向け課題解決
- 形式: 顔出しなし / カルーセル / テキスト中心短尺動画 / HPスクロール動画 / モックアップ / 前後比較 / 字幕解説 / 工程録画 / チェックリスト・図解・FAQ
- Canvaは無料プランで補助用途。Canva Proを必須にしない。**自動生成の中核はブランドテンプレートへコードで流し込む方式**(Satori/SVG/Sharp/Canvas等を比較し、文字切れ・誤字・解像度・フォント・一貫性を検証できる方式を提案 → `11`)
- 導線: 当面はInstagram DM。自社HP完成後はHP・実績・フォーム・相談予約へ誘導
- **AIはDM返信案を作るだけ。自動送信しない。価格・納期・契約条件をAIが確定しない**

## 6. 実績と権利

- HP制作実績3件。顧客名・サイト画面・URLはInstagramで公開可能(※設計上は同意管理を必須化 → `13`)
- 顧客評価は口頭のみ。**正式な推薦コメントとして使う前に内容確認と掲載許可を取得。許可前は顧客の発言として脚色・断定しない**
- 1件の実績から複数投稿(完成紹介・課題・工夫・スマホ対応・技術・工程・価値)へ展開する

## 7. 人間とAIの役割分担

**AI**: 情報収集と情報源記録 / 調査 / AI集客会議 / テーマ・カレンダー・台本 / コピー・CTA・ハッシュタグ / カルーセル構成・画像生成 / 実績投稿化 / 誤字・事実・ブランド・権利・リスク検査 / 結果整理・改善提案 / 週次月次レポート / DM要約・分類・見込み度・返信案

**代表者**: 1日最低30分 / 投稿案の承認・却下・修正指示 / DM返信の確認と送信 / 見積もり・納期・契約の決定 / 実績・素材の追加 / ブランド・事業・公開の重要判断

- **公開前は原則代表者の承認必須**。実績・料金・ニュース・第三者情報・顧客情報を含む投稿を無承認で公開しない
- 完全自動投稿はMVP必須条件ではない

## 8. AI組織(§9)

代表(人間) — AI社長補佐 — AIマーケティング部(戦略 / リサーチ / コンテンツ企画 / コピー / デザイン / 品質管理 / 分析 / 顧客対応)。
初期AI社員は9名で、名前と役職を持つ。**画面上9名でも9プロセスを常時並列実行しない**。必要な担当だけ順次呼び出し、情報を共有し重複処理を避ける。表示キャラクターと実行プロセスを分離する。

各AI社員に定義する項目: 名前候補・性格・目的・入力・出力・権限・禁止事項・使用可能ツール・モデル選択・失敗時処理・評価指標(→ `05`)

## 9. モデル・利用枠(§10)

- 設計=高推論モデル / 実装=Claude Code Opus想定 / 日常運用=Sonnet または軽量モデル中心 / 分類・整形・定型=さらに軽いモデルまたは通常コード / 高性能モデルは重要判断・難レビュー・失敗再検討のみ
- **Claude MaxプランがAnthropic API費用を含むと仮定しない。非公式な方法でMax認証情報を流用しない**
- API必須機能は追加費用・設定・代替案を明記する
- モデル名を直書きせず、役割/モデルプロファイルで切り替え可能にする
- キャッシュ・要約・差分処理・上限・無制限再試行防止を設ける
- Claude Codeの機能(モデル・サブエージェント・フック・権限・Webアクセス・スケジュール実行)は現行公式仕様とローカル環境で確認してから設計(→ `09` に確認結果)

## 12. UI(§13)

- 2Dピクセルアートのレトロゲーム風オフィス。代表者もアバターとして登場
- 必須体験: 始業で稼働 / タスク状態に応じた部屋移動 / 9状態(調査中・会議中・制作中・品質確認中・承認待ち・完了・待機・エラー・予算停止)の識別 / 社員クリックで詳細パネル / 承認・却下・修正 / 素材登録 / 議事録・日報週報月報閲覧
- 信頼性絶対条件: 実イベントと表示の同期 / 停止中に「作業中」と表示しない / 根拠のない進捗率を出さない / 演出状態と実状態を別データ管理 / エラー・待機・承認待ち理由を隠さない / 将来部門を実装済みに見せない
- 将来部門(営業・Web制作・開発・経理管理)は「準備中」の部屋。クリックで役割と解放条件のみ表示
- 品質: Next.jsデスクトップ中心+スマホ閲覧可 / ブランドカラーはトークン化 / 業務データは通常フォント / SVGアイコン(絵文字を操作アイコンにしない) / キーボード・フォーカス・コントラスト / 色だけで状態表現しない / prefers-reduced-motion / アニメーション無効の一覧表示 / 十分なタップ領域 / 重い3Dエンジン不使用 / 描画方式は比較の上選定 / 素材ライセンス記録

## 13. ワークフロー(§14) / 情報品質(§15) / KPI(§16) / セキュリティ(§17)

- 日次始業・投稿制作・DM支援の3ワークフローを状態遷移図・シーケンス図・例外フロー付きで設計(→ `06`)
- ニュースは タイトル・情報源URL・発行元・公開日・確認日 を保存。一次情報優先、単一情報源で断定しない、推測と事実を分離、引用・著作権配慮、不確実は除外or警告、効果保証・誇大広告表現の禁止
- KPIは現状値基準で30日ごとに再設定。目標値は根拠付き提案とし捏造しない(→ `15`)
- セキュリティ: 秘密情報をコード/Gitへ保存しない(.env.exampleのみ管理)/ 顧客公開許可をデータ管理 / 公開素材と機密素材の分離 / ログに個人情報・秘密を残さない / 必要に応じマスキング / 承認・却下・公開・修正の監査ログ / タスクの停止・再開・キャンセル / 再試行制限 / バックアップと復旧 / クラウド化時の認証・権限・暗号化・テナント分離を設計に残す

## 14. 1か月MVPの最優先成果(§18)

1. 2Dピクセルオフィスで実タスク状態を確認できる
2. 1つの始業コマンドで日次ワークフローを開始できる
3. 投稿テーマ・文章・カルーセル画像案を作成できる
4. 品質確認後、代表者が承認・却下・修正依頼できる
5. 投稿用ファイルを書き出せる
6. 実績素材から投稿案を作れる
7. 日報と基本的な利用量を確認できる

完全自動投稿・高度なMeta API・クラウド常時稼働・LINE通知・複数SNS同時運用は、MVPを遅らせる場合は第2段階以降。

## 15. 設計原則(§19)

ローカルファースト / モジュラーモノリス / 通常コードでできることにAIを使わない / AI出力は構造化+スキーマ検証 / 会社・部門・社員・タスク・成果物・承認・イベントを別エンティティ / UIはイベントログから状態再現 / 冪等な再実行 / プロバイダー・ストレージ・通知・SNSのアダプター化 / クラウド移行可能かつMVPを複雑にしない / 未確認のAPI・機能を前提にしない
