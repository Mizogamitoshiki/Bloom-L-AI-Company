# 16. テスト戦略

## 1. 方針

- AI出力の「内容の良し悪し」はテストで保証しない(QAエージェント+人間承認の役割)。テストが保証するのは**構造・状態遷移・安全装置・表示の正しさ**
- ツール【推奨】: Vitest(unit/integration)+ Playwright(E2E)+ axe-core(a11y)。すべて無料

## 2. テストレベル

### Unit(src/core中心)
| 対象 | 例 |
|---|---|
| Zodスキーマ | 全成果物スキーマの正常系/境界(文字数上限±1)/異常系 |
| イベントリデューサ | イベント列→タスク状態/社員表示状態の導出。heartbeat10分超→stale。**「runningイベントなしにworking表示にならない」** |
| 状態遷移ガード | 不正遷移(qa未通過→awaiting_approval等)が例外になること |
| 冪等性 | 同一idempotency_keyの再実行が新タスクを作らない |
| マスキング【第2段階 — DM支援実装時】 | 電話・メール・住所パターンの置換。ログ関数に本文を渡すと型エラー/実行時拒否 |
| 集計 | KPI計算・利用量集計の決定的検証 |

### Integration(CLI+DB)
- `company` CLI: submit(検証NG→拒否・イベント記録)/ run-start(異常終了回収)/ restore+doctor
- レンダラー: サンプルspec→PNG生成、寸法・ページ数検証、**文字あふれspecがエラーになること**、同一spec→同一出力(スナップショット比較)
- 承認API: 承認/却下/修正がapprovals+audit_logに記録され、posts状態が遷移する

### E2E(Playwright、デモデータ使用)
1. **始業→承認の主経路**: シードイベント投入→オフィス表示→社員クリック→詳細パネル→承認キュー→承認→書き出し→published記録
2. **信頼性シナリオ**: heartbeat停止データ→「状態不明」表示になる / エラータスク→理由表示
3. **修正ループ**: 修正依頼→drafting戻り→版が+1
4. **権利ブロック**: 許可未記録の実績投稿がQAで止まり「権利確認待ち」タブに出る
5. **アニメーションOFF/reduced-motion**: 一覧モード表示と情報等価性

### アクセシビリティ
- axe自動チェック(全画面、重大違反0)/ キーボードのみで承認操作が完了できるE2E / コントラストはトークン定義時に静的検証

## 3. デモモードとフィクスチャ

- `pnpm company seed --demo` で架空データ(架空顧客・架空ニュース)を投入。**UI全体に「デモデータ」バナー常時表示**(実データとの混同防止。プロンプト2の要件)
- デモデータには実在顧客名・実URLを含めない

## 4. 受け入れテスト(→20)

- `20-acceptance-criteria.md` の各ACに手動確認手順を対応付け、MVP完了時に代表者がチェックリストで検収
- AI実行を含む受け入れ(kickoff一巡)は、実際のClaude Codeセッションで1回以上実施し、runログを保存

## 5. CI【推奨・任意】

- GitHub Actions(無料枠): lint + unit + integration。E2Eはローカル実行(Playwright起動時間節約)。AI呼び出しはCIで行わない(費用・認証なし)

### V3追補(2026-07-13 実装反映)
- 追加テストスイート: `v3-gates`(QA構造ルール・禁止語・sources・権利・上限・旧データ互換)/ `v3-templates`(tpl-news/tpl-portfolioの5ページ・決定性・権利ゲート)/ `v3-review-fixes`(scope個別強制・上限境界値(未満/一致/超過/最終タスク/翌日維持)・URL検証)/ `migrations`(空DB・V2形式DB・再実行・途中失敗ロールバック・データ保持・FK/重複拒否・PRAGMA検証)
- マイグレーションのテストは `BASE_DDL`(V2形状)から実DB相当を構築して検証する
