## D-14 V5.4 クラウド対応基盤の方針(2026-07-17)

- **DB**: SQLiteをローカル運用の正として維持。`DATABASE_PROVIDER`(既定sqlite)で境界を明示し、postgresは「準備のみ」(スキーマ`src/adapters/db/postgres/schema.sql`+export/import-checkツール)。接続未実装の間はfail closedで停止し「対応済み」と偽装しない
- **移行先候補**: PostgreSQLはOSS(本体無料)。Neon Free / Supabase Free等を将来選択可能だが、**現時点で契約・作成しない**(月額追加0円維持。Q2の事前承認原則を継続)
- **安全ゲート**: Vercel Preview/テスト環境ではInstagram live投稿を構造的に禁止(解除不可)。Vercel productionは `META_PUBLISH_MODE=live` + `ALLOW_LIVE_INSTAGRAM_PUBLISH=true` の二重条件。ローカル代表者環境はV5.3手順を維持
- **認証**: 即席の簡易パスワード認証は作らない。cloud実行(`APP_RUNTIME_MODE=cloud`/VERCEL_ENV検出)で認証未確定の間は全変更系APIを拒否(fail closed)。PreviewはVercel Authenticationで保護するが、Production恒久認証とは区別する。方式確定までProduction公開禁止
- 詳細: `26-v54-vercel-cloud-readiness.md`

## D-17 Canva MCP試作の結論(2026-07-17、D-09の再確認)

- **試作内容**: Canva MCP(`generate-design`→`create-design-from-candidate`→`export-design`)で社内ダッシュボード用の汎用アバターアイコン(PNG 512×512、Instagram投稿とは無関係)を1件試作し、`apps/dashboard/public/avatars/canva-avatar-trial.png` として保存した。
- **結論: D-09§6の判定(補助用途のみ)を維持する**。理由:
  1. Canva出力は文字あふれ検査・レイアウト機械検証・フィンガープリント再現性(Satori+Sharpパイプラインの3層検証)を通せない。AI視覚QA頼みになり、Instagramカルーセルの確定投稿には引き続き使えない。
  2. `generate-design`は毎回AIが再生成する候補であり、同一入力からの決定的な再現ができない(D-09の「再現性」列で✕とした判定どおり)。
  3. 書き出しURLはS3署名付きURLで数時間~1日程度の有効期限があり、時間が経つと失効する(本セッションでも1回失効を確認)。取得したら即ダウンロードする運用が必要。
  4. Canva側に実デザインが作成される(アカウントに残る)ため、量産用途には向かない。
- **採用する用途**: オフィスUI(`apps/dashboard`)の非公開・社内向け装飾(社員アバターのプレースホルダー等)に限定して利用を許可する。Instagram投稿本番パイプライン(`src/adapters/render`)への組み込みは行わない。
- 参照: D-09。**→ D-18(2026-07-24)により改定: Instagram本番パイプラインへの採用を代表者が決定。**

## D-18 Canvaレンダリングの本番採用(2026-07-24、CEO決定によるD-17改定)

- **経緯**: 代表者(CEO)より「テンプレがダサい。Canvaを使ってAI社員が投稿内容を作成するように修正したい。妥協なしに実現させて」との明示指示。加えて2026-07-22/24の2日連続・2テンプレート(tpl-news/tpl-howto)・計3回のコピー改訂で視覚QAが「カード下部の空白過多」でfailし続けており、現行Satoriテンプレートのデザイン品質課題は記録済みの実在課題である。
- **決定**: Canva MCPによる投稿画像生成を**第一候補のレンダリング経路**として本番採用する(`company canva-register`)。Satori renderはフォールバックとして維持。
- **事前検証(2026-07-24)で確認した制約**:
  1. 本セッションのCanvaコネクタでは編集トランザクション・autofill・テキスト抽出(`get-design-content`)は**サーバー側で未提供**。「マスターテンプレート+文字流し込み」方式は不可能で、`generate-design`→書き出しのみが可能
  2. `generate-design`は試作4案中3案で文字事故(英語プレースホルダー混入・タイトル途中切れ・存在しないイベント日時の捏造・改行崩壊)。**毎回の目視照合が必須**
  3. 書き出しURLは短時間で失効する(即時ダウンロード運用)
- **D-17の懸念への補償(ガードは弱めず置き換える)**:
  1. 文字あふれ機械検査の代替: オーケストレーターが全候補サムネイル・全書き出しPNGを実際に開いてcopy JSONと逐語照合(kickoff手順4)+紫苑の視覚QAに逐語一致チェックを追加
  2. 再現性の代替: `post_renders.render_engine='canva'`とし、fingerprintを**画像内容ハッシュ(content-addressed)**に変更。export時に再計算一致を検査し、QA後の差し替え・改変を決定的に検知(`computeExternalRenderHash`)。コード版fingerprintより外部出力には厳密
  3. 整合チェーン維持: specは既存`buildSpecForPost`(権利・source前提検査込み)で最新copyから構築。「最新copy→spec→PNG一式」の不変ID連鎖・枚数/寸法機械検査・紫苑視覚QA(fail closed)・代表者承認(decidePost)は全経路共通で不変
  4. テンプレート版の代表者承認ゲートはcanva経路では適用外(毎回デザインが一意のため)。代わりに投稿単位の承認画面で実画像を確認する運用
- **実装**: migration 16(post_renders.render_engine/external_ref)、`src/adapters/canva/register.ts`、`company canva-register`、exportゲートのcanva分岐、`tests/v8-canva-register.test.ts`(6件)。
